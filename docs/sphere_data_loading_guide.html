Overview

This guide outlines the procedure to load the Sphere dataset (JSONL format) into an Oracle Globally Distributed Database (GDD) 26ai environment. The process utilizes **Sharded External Tables** mapped to local files on each shard and a **Hybrid Parallel Load** strategy to maximize throughput.

Architecture Overview

In an Oracle GDD architecture, data loading is most efficient when performed locally on each shard ("Direct Path Load"). The process follows this data flow:

1. Catalog Database

Global Schema (DDL) is defined once.

↓

Propagates to all Shards

Shard 1

Local `sphere.jsonl` is mapped.

Load Script Runs Locally

Shard 2

Local `sphere.jsonl` is mapped.

Load Script Runs Locally

Shard N...

Local `sphere.jsonl` is mapped.

Load Script Runs Locally

3. Shard-Pruned Loading

Each load script uses `SHARD_CHUNK_ID` to filter and insert **only** the rows that belong to that specific shard, discarding the rest.

Prerequisites

  • ✓

    Source Data

    The `sphere.jsonl` file must be present on the file system of **every shard node**. (Recommended: `/sphere/sphere.jsonl`)

  • ✓

    Storage

    Ensure `sphere_ts1` tablespace storage is adequate on all shards.

  • ✓

    System Configuration

    Redo Logs: Min **4GB** per group (Critical for performance).

    Recovery Area: Increase `db_recovery_file_dest_size` to handle load volume (e.g., 2TB).

Loading Process

Step 1

Global Schema Setup (Catalog)

Run this script **once** on the Catalog database as SYSDBA. It creates the global `sphere_user`, the sharded `sphere_documents` table, and propagates the DDL to all shards.

Script: 01_catalog_schema_setup.sql

sqlplus sys/<password>@<catalog_host>:<port>/<service_name> as sysdba @01_catalog_schema_setup.sql
Step 2

Local External Table Setup (All Shards)

Connect to **each Shard PDB individually** as `sphere_user`. This script disables Shard DDL to create a *local* directory and external table pointing to the `sphere.jsonl` file on that specific shard's file system.

Script: 02_shard_external_table_setup.sql

sqlplus sphere_user/<password>@<shard_host>:<port>/<pdb_service_name> @02_shard_external_table_setup.sql
Step 3

Hybrid Parallel Load (All Shards)

Execute this load script as `sphere_user` on **every shard server**, preferably in the background using `nohup`. This script uses a **Hybrid Load Strategy** (Parallel Read / Serial Write) to prevent "Log Buffer Space" contention.

Script: 03_hybrid_load_script.sql

nohup sqlplus sphere_user/<password>@<shard_host>:<port>/<pdb_service_name> @03_hybrid_load_script.sql > load_shard_$(date +%Y%m%d).log 2>&1 &

Monitoring

Check the log file or query active sessions:

SELECT status, count(*) FROM v$px_session WHERE username = 'SPHERE_USER' GROUP BY status;
Step 4

Post-Load Vector Indexing (Catalog)

**After** the load completes on all shards, connect to the **Catalog** as `sphere_user` to create the Vector Index. This DDL will propagate to all shards, and the index will be built locally in parallel.

Script: Post-Load Indexing (SQL)

-- Connect to Catalog
ALTER SESSION ENABLE SHARD DDL;
ALTER SESSION ENABLE PARALLEL DDL;

CREATE VECTOR INDEX sphere_doc_vector_idx ON sphere_documents(vector)
ORGANIZATION NEIGHBOR GRAPH
DISTANCE METRIC COSINE
WITH TARGET ACCURACY 90
PARALLEL 32;

Overview

The Meta Sphere dataset represents one of the largest publicly available corpus of web-scale text embeddings, containing approximately 900 million documents from Common Crawl with pre-computed 768-dimensional dense vector representations. Each document includes the original text, metadata, and a FLOAT32 vector embedding generated using the Sphere DPR (Dense Passage Retrieval) model.

This dataset serves as a critical benchmark for evaluating vector search systems at scale, particularly for retrieval-augmented generation (RAG) and semantic search applications where query latency and accuracy must remain consistent across billions of vectors.

This guide details the procedure for ingesting the complete Sphere dataset into Oracle Globally Distributed Database 26ai. The loading strategy employs external tables, enabling file-based data ingestion on each shard. We combine parallel query on the external table with direct-path insert operations to optimize throughput while minimizing redo log contention during high-volume ingestion.

Why Distributed Databases for Large Vector Datasets?

Vector datasets at the scale of Meta Sphere (900M+ records, ~200GB+ of dense embeddings) exceed the memory capacity constraints of single-node database systems. Distributed database architectures address this limitation through horizontal partitioning, distributing data across multiple nodes where each node maintains a subset of the total dataset in its local memory.

Oracle Globally Distributed Database implements shared-nothing architecture with Consistent Hash partitioning, enabling in-memory HNSW vector indexes to span multiple shards. This approach scales aggregate memory capacity linearly with node count while maintaining query performance through parallel execution and data locality.

Memory Constraints

  • In-memory HNSW vector indexes deliver significantly faster performance compared to disk-based IVF indexes
  • HNSW indexes utilize the Vector Memory Pool, a dedicated memory area within the System Global Area (SGA)
  • Single database instance memory is bounded by physical hardware constraints
  • Large vector datasets (500M+ vectors with high dimensionality) can exceed single-instance Vector Memory Pool capacity

Disk-Based Limitations

  • IVF vector indexes support datasets limited only by available tablespace storage
  • Storage costs are lower compared to memory requirements
  • Query performance degrades significantly compared to in-memory HNSW due to physical I/O overhead
  • Query latency may exceed acceptable thresholds for latency-sensitive workloads

Sharded In-Memory Vector Indexes

Distributed HNSW indexes across sharded databases scale memory capacity horizontally while maintaining query performance through parallel execution.

Scalability

  • Up to 1,000 shards per configuration
  • Consistent Hash partitioning
  • Linear memory capacity scaling

Performance Benefits

  • Sub-second query latency at scale
  • Parallel DDL index builds
  • Linear reduction in build time

Architecture Overview

The loading strategy uses three standard distributed database techniques:

  1. Global Data Services (GDS) propagates schema DDL from the catalog to all shards
  2. Local file access - source files reside on local storage at each shard node, accessed via external tables
  3. Chunk-aware filtering - the SHARD_CHUNK_ID function filters rows during query execution, ensuring each shard processes only data matching its assigned hash range

Direct-path INSERT with the APPEND hint bypasses the Database Buffer Cache to optimize throughput.

Prerequisites

Source Data Staging

The sphere.jsonl source file must exist on the local file system of every shard node.

  • Path: Recommended path is /sphere/sphere.jsonl
  • I/O Considerations: Store on high-performance local NVMe or SSD storage. Avoid NFS.

Storage Provisioning

  • Tablespace: Configure sphere_ts1 with AUTOEXTEND ON
  • Fast Recovery Area: Increase db_recovery_file_dest_size to accommodate archive logs (e.g., 2TB)

System Tuning

Redo Log Configuration: Set Redo Log group size to minimum 4GB.

Small log files trigger frequent log switches and checkpoints, interrupting direct-path load operations and degrading performance.

Step 1: Schema Setup (Catalog)

Target: Catalog Database | User: SYS (SYSDBA/GSMADMIN_ROLE)

Define the global data model on the Catalog. Execution propagates schema definitions to all registered shards via Global Data Services.

Technical Actions

  • Creates the all-shard user sphere_user
  • Defines sharded table sphere_documents using Consistent Hash Partitioning
  • Instantiates VECTOR(768, FLOAT32) column for embeddings

Execution:

sqlplus sys/<password>@<catalog_host>:<port>/<service_name> as sysdba @01_catalog_schema_setup.sql

Step 2: Local External Table Setup

Target: Each Shard PDB | User: sphere_user

Establish the link between database instance and local file system. Directory objects and external table definitions are instance-specific.

Important: Script executes ALTER SESSION DISABLE SHARD DDL to prevent GDD replication of local file system paths.

Execution (on each shard):

sqlplus sphere_user/<password>@<shard_host>:<port>/<pdb_service_name> @02_shard_external_table_setup.sql

Step 3: Data Load Execution

Target: Each Shard PDB | User: sphere_user | Method: Background execution (nohup)

Execute data ingestion using parallel query on the external table combined with serial direct-path insert.

Parallel Query

PARALLEL hint instantiates parallel query servers for reading, JSON parsing, and vector deserialization.

Serial Direct-Path INSERT

Parallel DML is not enabled to avoid redo allocation latch contention. Serializes redo generation within LGWR capacity.

Execution (on each shard):

nohup sqlplus sphere_user/<password>@<shard_host>:<port>/<pdb_service_name> @03_data_load_script.sql > load_shard_$(date +%Y%m%d).log 2>&1 &

Monitoring

Parallel Execution Server Status

Query V$PX_SESSION to verify active parallel execution servers:

SELECT sid, serial#, qcsid, degree, req_degree, server_group, server_set
FROM v$px_session 
WHERE qcsid = (SELECT sid FROM v$session WHERE username = 'SPHERE_USER');

Long Operations Monitoring

Query V$SESSION_LONGOPS to track progress:

SELECT opname, target, sofar, totalwork, units, time_remaining, elapsed_seconds
FROM v$session_longops
WHERE time_remaining > 0 AND username = 'SPHERE_USER';

Step 4: Post-Load Vector Index Creation

Target: Catalog Database | User: sphere_user

Vector index creation constructs an in-memory HNSW graph structure. Best practice defers index creation until bulk loading completes to avoid fragmentation.

Index Configuration

  • Organization: ORGANIZATION NEIGHBOR GRAPH (in-memory HNSW)
  • Distance Function: DISTANCE COSINE
  • Parallel DDL: Enables parallel index build on each shard
  • DDL Propagation: GDS propagates to all shards automatically

Execution (Catalog only):

ALTER SESSION ENABLE SHARD DDL;
ALTER SESSION ENABLE PARALLEL DDL;

CREATE VECTOR INDEX sphere_doc_vector_idx ON sphere_documents(vector)
ORGANIZATION NEIGHBOR GRAPH
DISTANCE METRIC COSINE
WITH TARGET ACCURACY 90
PARALLEL 32;
